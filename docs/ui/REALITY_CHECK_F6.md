# F6 Quality and Security Audit

Date: 2026-10-02
Branch: `codex/f6-quality`, based on F5 commit `4cb9161`
Audit type: static, read-only inspection of tool dispatch, process launch, messaging, email, and dependency call sites.

## Security findings

No tool was executed during this audit. In particular, no shell-injection payload was run, no email or message was sent, and no desktop action was invoked. Findings below are based on source paths and dispatcher behavior.

### P1 — Windows URL launch passes tool input to a shell

`actions/open_app.py::_launch_windows` has two `shell=True` call sites. The first passes `app_name` directly to `Popen` after a `shutil.which` check (`actions/open_app.py:92-104`). The fallback passes `f"start {app_name}"` when the value contains a colon (`actions/open_app.py:106-111`). `app_name` originates from the `open_app` tool argument. A URL containing Windows command separators such as `&` or `|` can be parsed as another shell command by the fallback. The `shutil.which` check does not protect that fallback.

**Recommended correction:** open URL schemes through a non-shell URL API and launch executable paths with argument lists and `shell=False`; validate application names against supported launch targets. No correction was made because this changes tool behavior and requires user approval under the mission.

### P2 — Dev-agent editor launch retains shell execution

`actions/dev_agent.py:273-292` uses `Popen([cmd, str(project_dir)], shell=True)`. The executable choices are fixed candidates, while the project directory is generated by the dev-agent flow. Static review did not establish a directly exploitable command injection path, but shell parsing is unnecessary here and expands the execution surface.

**Recommended correction:** use `shell=False` with the existing argument list and test the supported Windows launch paths. No behavior change was made.

### P3 — Brightness shell commands are fixed strings

`actions/computer_settings.py:131-137` and `160-166` call `xrandr` through `shell=True`. The command strings contain fixed shell syntax and values read from local `xrandr` output; this review found no caller-controlled parameter interpolated into either string. This is still avoidable shell use, but no direct input-injection path was established.

**Recommended correction:** replace the pipelines with argument-list subprocess calls and parse output in Python, with platform tests. No change was made.

### P1 — High-impact actions rely on model instructions rather than a dispatcher approval gate

`main.py::_execute_tool` dispatches mutating functions directly. `_execute_tool_batch` serializes a group containing mutating calls (`main.py:1730-1741`), but it does not validate that the current user turn authorized each side effect.

- `computer_control` reaches typing, clipboard, mouse, and keyboard operations directly from model-supplied arguments (`main.py:1640-1642`; `actions/computer_control.py:383-441`). There is no user-confirmation token or code-level preflight in this dispatch path. The system prompt provides typing restrictions at `core/prompt.txt:18`, so enforcement currently depends on model compliance.
- `dev_agent` can create and write project files, install dependencies, open VS Code, and run generated code (`main.py:1613-1615`; `actions/dev_agent.py:238-271, 273-292, 294-347`). Its tool schema describes project creation but does not require a separate approval step (`main.py:682-693`).
- `email_control` has a prepare/approve flow and checks the visible Gmail recipients, subject, and body before sending (`actions/email_control.py:789-824`). However, the dispatcher accepts `action="approve"` from a tool call without checking for a later, explicit user-confirmation event tied to that exact pending draft (`main.py:1571-1576`, `actions/email_control.py:1265-1278`). The prompt instructs the model to wait for confirmation, but the code does not enforce it.
- `send_message` sends a user-authored message directly by design when the user asks (`core/prompt.txt:14`, `main.py:1567-1569`). This is consistent with the current prompt policy, but authorization is not independently enforced in code. JARVIS-authored replies use a separate prepare/approve lifecycle, which has the same dispatcher boundary.

**Recommended correction:** add a dispatcher-level approval record bound to the initiating user turn and the exact operation or draft; reject any approval action without a matching later user confirmation. Preserve the current direct-send policy only where the application can verify an explicit user request. This changes tool behavior and was not implemented.

### Fail-closed power-action gate is not reachable through the declared tool schema

`actions/computer_settings.py:695-706` requires a clear computer target and `confirmed=yes` for restart/shutdown actions. The `computer_settings` schema in `main.py:591-599` does not expose a `confirmed` field, so the model cannot satisfy the second check through the declared function contract. This currently prevents the power action from running through this tool path; it is a usability/schema mismatch, not an approval bypass. Any repair should make confirmation come from an independently verified later user turn rather than simply allowing the model to set a boolean.

## Dependency changes

- `requirements-desktop.txt` contains the local desktop runtime and optional integrations.
- `requirements-api.txt` contains hosted-service dependencies and the direct imports needed when the API creates `JarvisLive`.
- `requirements-dev.txt` installs both runtime profiles plus pytest for CI and local development.
- `requirements.txt` remains a backwards-compatible aggregate used by existing setup and launcher scripts.
- The UTF-8 BOM was removed from the root manifest.
- Both Gemini SDK distributions remain. `google-generativeai` is imported at runtime by `actions/code_helper.py`, `actions/computer_settings.py`, `actions/desktop.py`, `actions/dev_agent.py`, `actions/flight_finder.py`, `actions/youtube_video.py`, `agent/error_handler.py`, `agent/executor.py`, and `agent/planner.py`. Removing it before those call sites are migrated would break those actions.

The hosted API profile includes `google-genai`, `google-generativeai`, and `sounddevice` because the API's WebSocket route creates `JarvisLive` from `main.py`, which imports those packages at module load and exposes legacy-SDK actions.
